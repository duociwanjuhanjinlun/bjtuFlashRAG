# BM25与E5并行检索方案

## 一、问题背景

当前项目使用E5向量检索（`intfloat/e5-base-v2`）作为主要检索方式，但在实际使用中发现存在以下问题：

1. **专有名词匹配不精准**：向量检索在语义相似度匹配方面表现良好，但对于精确的专有名词（如人名、地名、机构名等）的匹配能力较弱
2. **词级精确匹配缺失**：E5等向量模型更关注语义相似性，可能无法准确匹配查询中的关键实体词

## 二、解决方案思路

### 2.1 核心思想

采用**混合检索（Hybrid Retrieval）**策略，将基于词匹配的BM25检索器和基于语义的E5向量检索器并行使用，通过优势互补提升检索效果：

- **BM25的优势**：基于词频和逆文档频率，擅长精确匹配专有名词和关键词
- **E5的优势**：基于语义理解，擅长捕捉语义相似性和上下文关联
- **并行使用**：两种检索方式同时进行，然后合并结果，既保证精确匹配，又保留语义理解能力

### 2.2 FlashRAG中的现有实现

FlashRAG代码库中已经提供了多检索器支持的基础设施：

#### 2.2.1 核心代码位置

1. **MultiRetrieverRouter类**：
   - 位置：`/root/FlashRAG/flashrag/retriever/retriever.py`（第585行开始）
   - 功能：管理多个检索器，支持并行检索和结果合并

2. **检索器初始化**：
   - 位置：`/root/FlashRAG/flashrag/utils/utils.py`（第72-101行）
   - 函数：`get_retriever(config)`
   - 当配置中`use_multi_retriever: True`时，会自动使用`MultiRetrieverRouter`

3. **BM25检索器**：
   - 位置：`/root/FlashRAG/flashrag/retriever/retriever.py`（第226行开始）
   - 类：`BM25Retriever`
   - 支持两种后端：`pyserini`和`bm25s`

4. **E5向量检索器**：
   - 位置：`/root/FlashRAG/flashrag/retriever/retriever.py`（第352行开始）
   - 类：`DenseRetriever`
   - 当前项目使用的E5模型通过此类实现

#### 2.2.2 合并策略

`MultiRetrieverRouter`支持三种结果合并方法：

1. **concat（拼接）**：简单拼接两个检索器的结果，去重后返回
2. **rrf（Reciprocal Rank Fusion）**：使用RRF算法融合两个检索器的排序结果
3. **rerank（重排序）**：使用reranker模型对所有合并后的文档进行重新排序

### 2.3 索引和语料库路径说明

#### 2.3.1 平台提供的资源

根据项目要求，英博云平台提供了以下知识库资源：

- **语料库文件**：`/public/modelscope-datasets/hhjinjiajie/FlashRAG_Dataset/retrieval_corpus/wiki18_100w.jsonl`
- **E5向量索引**：`/public/modelscope-datasets/hhjinjiajie/FlashRAG_Dataset/retrieval_corpus/wiki18_100w_e5.index`
- **E5模型路径**：`/public/huggingface-models/intfloat/e5-base-v2`

**注意**：平台**只提供了E5索引**，**没有提供BM25索引**，因此需要自己构建BM25索引。

#### 2.3.2 构建BM25索引

BM25索引需要基于语料库文件构建。BM25是基于词频统计的检索方法，**不需要模型**，只需要语料库文件。

**两种后端对比**：

| 特性 | pyserini | bm25s |
|------|----------|-------|
| **底层实现** | 基于Java Lucene | 纯Python实现（使用numba加速） |
| **安装复杂度** | 较复杂，需要Java环境 | 简单，纯Python包 |
| **中文支持** | ✅ 支持较好（有专门的中文模式） | ⚠️ 支持一般（代码注释：not support chinese well） |
| **批量检索** | 循环调用单个检索（效率较低） | 真正的批量处理（效率较高） |
| **索引大小** | 可能包含文档内容，索引较大 | 不包含文档内容，索引较小 |
| **检索速度** | 中等 | 较快（numba加速） |
| **维护状态** | ⚠️ 将被弃用（FlashRAG官方说明） | ✅ 推荐使用（FlashRAG推荐） |
| **适用场景** | 中文语料库，需要更好的中文分词 | 英文语料库，或需要更快的检索速度 |

**选择建议**：
- **推荐使用bm25s**：经过检查，`wiki18_100w.jsonl`语料库主要是英文内容（中文文档占比约0.43%），bm25s对英文支持很好，且速度更快、安装更简单
- **备选pyserini**：如果bm25s遇到问题，可以使用pyserini，它对中英文混合内容支持更全面

**语料库语言分布说明**：
- 语料库名称虽然叫`wiki18_100w`，但经过抽样检查，主要是英文内容
- 中文内容占比很低（约0.43%），主要是中文地名、人名等
- 因此更适合使用bm25s后端

**构建命令**（推荐使用bm25s后端，语料库主要是英文）：

```bash
# 在/root下创建索引目录
mkdir -p /root/deepsearch_flashrag/indexes/bm25_index

python -m flashrag.retriever.index_builder \
    --retrieval_method bm25 \
    --corpus_path /public/modelscope-datasets/hhjinjiajie/FlashRAG_Dataset/retrieval_corpus/wiki18_100w.jsonl \
    --bm25_backend bm25s \
    --save_dir /root/deepsearch_flashrag/indexes/bm25_index/
```

**或者使用pyserini后端**（备选方案）：

```bash
# 在/root下创建索引目录
mkdir -p /root/deepsearch_flashrag/indexes/bm25_index

python -m flashrag.retriever.index_builder \
    --retrieval_method bm25 \
    --corpus_path /public/modelscope-datasets/hhjinjiajie/FlashRAG_Dataset/retrieval_corpus/wiki18_100w.jsonl \
    --bm25_backend bm25s \
    --save_dir /root/deepsearch_flashrag/indexes/bm25_index/
```

**说明**：
- `--retrieval_method bm25`：指定构建BM25索引
- `--corpus_path`：使用平台提供的语料库文件
- `--bm25_backend`：选择后端，`pyserini`或`bm25s`
  - **bm25s**（推荐）：轻量级，安装简单，检索速度快，对英文支持很好。**适合当前语料库**（主要是英文内容）
  - **pyserini**：中文支持更好，但安装较复杂。适合中英文混合或中文为主的语料库
- `--save_dir`：索引保存目录（构建完成后，索引会保存在`save_dir/bm25/`目录下）

**重要提示**：
- 构建时使用的`--bm25_backend`必须与配置文件中`bm25_backend`一致
- 如果构建时使用pyserini，配置文件中也必须设置为pyserini

**构建完成后的索引路径**：
- 如果使用pyserini：`/root/deepsearch_flashrag/indexes/bm25_index/bm25/`
- 如果使用bm25s：`/root/deepsearch_flashrag/indexes/bm25_index/bm25/`

**构建时间估算**：
- 语料库大小：约2100万文档，13GB
- **pyserini后端**：预计需要 **30分钟到2小时**（取决于服务器性能）
- **bm25s后端**：可能稍快一些，预计需要 **20分钟到1.5小时**
- 建议在构建时监控进度，如果超过3小时仍未完成，可能需要检查是否有问题

### 2.4 配置方式

在FlashRAG中启用多检索器需要在配置文件中设置：

```yaml
use_multi_retriever: True
multi_retriever_setting:
  merge_method: "rrf"  # 或 "concat" 或 "rerank"
  topk: 50  # 最终返回的文档数量
  retriever_list:
    - retrieval_method: "bm25"
      index_path: "/root/deepsearch_flashrag/indexes/bm25_index/bm25"
      corpus_path: "/public/modelscope-datasets/hhjinjiajie/FlashRAG_Dataset/retrieval_corpus/wiki18_100w.jsonl"
      retrieval_topk: 30  # BM25检索的topk
      bm25_backend: "bm25s"  # 推荐使用bm25s（语料库主要是英文），或 "pyserini"，需与构建时使用的后端一致
    - retrieval_method: "e5"
      retrieval_model_path: "/public/huggingface-models/intfloat/e5-base-v2"
      index_path: "/public/modelscope-datasets/hhjinjiajie/FlashRAG_Dataset/retrieval_corpus/wiki18_100w_e5.index"
      corpus_path: "/public/modelscope-datasets/hhjinjiajie/FlashRAG_Dataset/retrieval_corpus/wiki18_100w.jsonl"
      retrieval_topk: 30  # E5检索的topk
      retrieval_pooling_method: "mean"
      retrieval_use_fp16: True
      retrieval_batch_size: 2
      retrieval_query_max_length: 1024
```

**重要提示**：
1. **BM25不需要model_path**：BM25是基于词频统计的，不需要模型文件
2. **corpus_path相同**：BM25和E5使用相同的语料库文件，确保文档ID一致
3. **bm25_backend需一致**：配置中的`bm25_backend`必须与构建索引时使用的后端一致

## 三、实现方案设计

### 3.1 架构设计

如果后续需要实现，建议采用以下架构：

```
┌─────────────────────────────────────────┐
│      HybridRetriever (独立模块)          │
├─────────────────────────────────────────┤
│  - BM25Retriever (词匹配)                │
│  - DenseRetriever (E5语义检索)           │
│  - ResultMerger (结果合并)               │
└─────────────────────────────────────────┘
         │
         ├─> 并行检索
         │   ├─> BM25检索 (ThreadPoolExecutor)
         │   └─> E5检索 (ThreadPoolExecutor)
         │
         └─> 结果合并
             ├─> 去重
             ├─> 分数归一化
             └─> 融合排序 (RRF/加权融合)
```

### 3.2 关键设计点

1. **独立模块化**：
   - 创建独立的`HybridRetriever`模块，不修改FlashRAG核心代码
   - 可以放在`/root/deepsearch_flashrag/retriever/`目录下
   - 继承或封装FlashRAG的`BaseRetriever`接口，保持兼容性

2. **并行执行**：
   - 使用`ThreadPoolExecutor`或`as_completed`实现真正的并行检索
   - FlashRAG的`MultiRetrieverRouter`已经实现了并行（第689行使用ThreadPoolExecutor）

3. **结果合并策略**：
   - **推荐使用RRF**：Reciprocal Rank Fusion能够有效融合不同检索器的排序信息
   - 也可以尝试加权融合：根据BM25和E5的特点，给不同检索器设置不同权重
   - 对于专有名词查询，可以给BM25更高的权重

4. **性能优化**：
   - 复用语料库加载（FlashRAG的MultiRetrieverRouter已经实现）
   - 支持批量检索以提高效率
   - 考虑缓存机制，避免重复检索

### 3.3 预期效果

1. **专有名词匹配提升**：BM25能够精确匹配查询中的专有名词，特别是人名、地名等
2. **语义理解保留**：E5继续提供语义相似性匹配能力
3. **召回率提升**：两种检索方式互补，能够召回更多相关文档
4. **准确率提升**：通过RRF等融合策略，相关文档的排序更加合理

## 五、注意事项

1. **索引一致性**：
   - **必须**确保BM25索引和E5索引使用相同的语料库文件（`wiki18_100w.jsonl`）
   - 否则文档ID不匹配，会导致结果合并错误
   - 平台提供的语料库路径：`/public/modelscope-datasets/hhjinjiajie/FlashRAG_Dataset/retrieval_corpus/wiki18_100w.jsonl`

2. **BM25索引构建**：
   - 平台**只提供了E5索引**，BM25索引需要自己构建
   - 构建命令见2.3.2节
   - 构建时间取决于语料库大小，100万文档可能需要一些时间

3. **后端选择**：
   - **推荐使用pyserini**：对中文支持更好，且更稳定
   - bm25s：速度可能更快，但对中文支持可能不如pyserini
   - 配置中的`bm25_backend`必须与构建时使用的后端一致

4. **资源消耗**：
   - 并行检索会增加内存和计算资源消耗
   - BM25索引会占用一定磁盘空间
   - 需要合理设置topk，避免资源耗尽

5. **合并策略选择**：
   - 不同数据集和查询类型可能适合不同的合并策略
   - 建议先尝试RRF，如果效果不好再尝试rerank
   - 需要实验验证哪种策略最适合当前任务

6. **配置复杂度**：
   - 多检索器配置相对复杂，需要仔细检查配置项
   - 特别注意路径是否正确，特别是BM25索引路径

## 八、总结

BM25与E5并行检索是一个成熟的混合检索方案，能够有效解决向量检索在专有名词匹配上的不足。FlashRAG已经提供了良好的基础设施支持，可以通过配置直接使用，也可以在此基础上进行扩展优化。

**关键要点**：
1. 平台只提供了E5索引，**BM25索引需要自己构建**
2. 构建BM25索引使用相同的语料库文件（`wiki18_100w.jsonl`）
3. 推荐使用pyserini后端构建BM25索引（对中文支持更好）
4. 配置时确保BM25和E5使用相同的`corpus_path`
5. 建议先尝试使用FlashRAG的`MultiRetrieverRouter`，根据实际效果再决定是否需要独立实现

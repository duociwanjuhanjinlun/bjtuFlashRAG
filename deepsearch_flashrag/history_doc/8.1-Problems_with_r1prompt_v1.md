### 一、 Prompt 层面的改良 (针对提供的代码)

你目前的 Prompt 极度强调 "Concise" (简洁) 和 "Short" (简短)。这在**推理（Reasoning）阶段可能是个陷阱**。

**问题所在：**
DeepSeek-R1 或类似的推理模型，需要通过"漫长"的思维链来分解复杂问题。如果你强制它 `<think>` 也要 concise，它就没有足够的空间去**拆解问题**和**构建高质量的关键词**。它可能会直接抛出原问题去搜索，导致检索失败。

**修改建议：**

1.  **引入 Few-Shot (少样本示例)：** 告诉模型什么样的 Search Query 是好的。E5 和 BM25 对关键词敏感，对自然语言长句（尤其是疑问句）处理较差。
2.  **解除 `<think>` 的长度限制：** 鼓励它在 `<think>` 里做 "Query Decomposition" (问题拆解)。
3.  **强制关键词优化：** 明确要求 `<search>` 标签内使用关键词而非整句。

**改良后的 Prompt 代码示例：**

```python
from flashrag.prompt.base_prompt import PromptTemplate

class BetterSearchR1PromptTemplate(PromptTemplate):
    """
    优化后的 Prompt：
    1. 增加了 Few-shot 示例，指导模型如何生成好的搜索词。
    2. 移除了对 <think> 的 'short' 限制，鼓励通过 CoT 拆解复杂问题。
    """
    
    R1_IMPROVED_INSTRUCTION = (
        "You are an expert reasoning assistant. Answer the user's question precisely using the provided tools.\n\n"
        "**Guidelines:**\n"
        "1. **Deep Reasoning (<think>)**: Analysis the user's request carefully inside <think> tags.\n"
        "   - Break down complex questions into sub-questions.\n"
        "   - Decide what specific entities or facts you need to verify.\n"
        "   - **Critique your own search queries** before using them.\n"
        "2. **Effective Search (<search>)**: If information is missing, use <search>keywords</search>.\n"
        "   - **IMPORTANT**: Do NOT input full sentences or questions in <search>.\n"
        "   - Use specific, high-value keywords (e.g., instead of 'who is the director of movie X', use 'movie X director').\n"
        "3. **Final Answer (<answer>)**: Output the final answer inside <answer> tags without explanation.\n\n"
        "**Examples:**\n"
        "User: Who is the wife of the actor who played Tony Stark?\n"
        "<think>\n"
        "1. Identify the actor who played Tony Stark. -> Robert Downey Jr.\n"
        "2. Need to find Robert Downey Jr.'s wife.\n"
        "Query strategy: Search for the actor's name and 'wife' or 'spouse'.\n"
        "</think>\n"
        "<search>Robert Downey Jr. wife</search>\n\n"
        "**Task:**\n"
        "Question: {question}\n"
    )

    def __init__(self, config, **kwargs):
        super().__init__(
            config,
            system_prompt="",
            user_prompt=self.R1_IMPROVED_INSTRUCTION,
            **kwargs
        )
```

### 二、 检索器配置层面的排查 (Technical Check)

拥有 E5 和 BM25 并不代表它们在"正确工作"。请检查以下硬伤：

#### 1\. E5 的 ` query:  ` 前缀 (至关重要)

E5 模型（如 `e5-large-v2` / `mistral`）在训练时使用了非对称指令。

  * **查询侧 (User Query)**：必须加前缀 `"query: "`。
  * **文档侧 (Database)**：通常需要 `"passage: "` (视具体版本而定，indexed 时如果没有加，query 时也不能乱加)。
  * **检查点：** 你的代码在调用 `retriever.search(query)` 之前，是否给 `query` 加上了前缀？如果没有，E5 的性能会下降 20% 以上。

#### 2\. 混合检索的权重 (Fusion)

  * BM25 擅长精确匹配（专有名词），E5 擅长语义匹配。
  * **问题：** 这里的 `Wiki18` 数据集可能包含大量专有名词。如果你的系统只是简单地相加分数，BM25 的分数范围（0-infinity）和 E5 的余弦相似度（0-1）不在一个量级。
  * **建议：** 确保使用了 **RRF (Reciprocal Rank Fusion)** 或者对分数进行了 **归一化 (Normalization)** 再加权。如果还没做，建议先无脑上 RRF。

#### 3\. Reranker 的 Top-K 窗口

  * **现状：** 检索差可能是因为"召回"阶段漏掉了文档，或者"重排"没排上来。
  * **建议：**
      * **Retrieval Top-K：** 建议设大一点（例如 50 或 100）。
      * **Rerank Top-K：** 最终给 LLM 的文档选 Top 5 或 Top 10。
      * 如果 Retrieval 只取了 Top 5 就直接喂给 LLM，Reranker 就失去了意义（因为它没有足够的候选集来挑选）。

### 三、 系统架构与数据层面的改良

#### 1\. 文档切片 (Chunking) 与 Refiner

  * Wiki 数据通常很长。如果你的 Chunk Size 太大（例如 1000 tokens），E5 的向量表征会被稀释（"lost in the middle"）。
  * **建议：** 检查 `Wiki18_100w` 的切片大小。一般推荐 256 - 512 tokens，并带有一定的 overlap。
  * **关于 Refiner：** 你安装了 Refiner，但如果它是在检索**前**对 Query 进行改写，可能会和你的 `<think>` 逻辑冲突。如果是在检索**后**对文档进行压缩（Extractive Refiner），请确保它没有把关键实体（Entity）给“压缩”没了。在 Debug 阶段，**建议先关掉 Refiner**，排除干扰变量。

#### 2\. 迭代式检索 (Iterative Retrieval) 的逻辑

你的 Prompt 暗示了这是一个 Agent（SearchR1）。

  * **单步 vs 多步：** 如果问题是 *"XX电影导演的出生地的市长是谁？"*，一次检索是搞不定的。
  * **逻辑检查：** 你的系统是否支持**多轮** `<search>`？
      * 如果系统只能执行一次搜索，那么 Prompt 必须被训练成生成"包含所有潜在关键词"的宽泛查询。
      * 如果支持多轮，Prompt 需要学会根据第一次的 `<information>` 结果，发起第二次 `<search>`。
